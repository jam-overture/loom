## What happened

#353 merged at 15:25 on 23 September. `Loom merge` had merged `main` into the
branch and pushed, which woke this session. Running the gate on that merged head
came back **red**, naming a file no lane had touched:

```
.next/types/validator.ts(395,39): error TS2307: Cannot find module
  '../../app/(docs)/docs/search-index/prose/route.js'
```

It was not the tree. `apps/loom/.next` is gitignored, so `git checkout` leaves
it alone, and this one was three days old — written by #353's own verify on 20
September, when `search-index/prose/route.js` was a route. `Loom docs` has since
made it dynamic, `prose/[section]/route.ts`. Next's generated route validator
still named the old path, and `@loom/app`'s `typecheck` reads that validator.

`rm -rf apps/loom/.next`, same commit, exit 0. **#353 was green all along** and
was verified as such before it landed.

## Why it was worth stopping for

**The error names another lane's file.** It reads as `Loom docs` having broken
the build, and everything the governance trains says a red gate is work now. The
moves available to a run that believes it are all worse than the cycle it cost
here: "fixing" a route that is already correct, editing outside its lane to do
it, or concluding a test is wrong — which the standards forbid in as many words.
Nothing in the message says the failing file is a build artifact.

**`pnpm clean` did not remove it.** It was `rm -rf dist` — the runtime's
artifacts, not the application's. The one command whose name says *clean* left
the cause in place.

## What changed

One line. `clean` is now `rm -rf dist apps/loom/.next`.

That is a mitigation and the report should not dress it up as a cure. The
structural cause is an ordering one: `@loom/app`'s verify is `typecheck && test
&& build`, and `.next/types/validator.ts` is **generated by** `next build` — so
the gate typechecks against the route map of the *previous* build every time.
Correct whenever the last build was this tree; stale exactly when it was not.

**Not decided here**, and the finding carries the three shapes with their costs:
build before typechecking (correct, and makes the fastest check wait on the
slowest for every lane on every run); exclude `.next/types` from the
application's tsconfig (cheap, and gives up catching a `Link` to a route that
does not exist); or have the gate clear `.next` first (honest, and throws away
the incremental build every run for a fault that only appears after a checkout
across a route change).

Left open because the application's build configuration is the shell's and the
cost lands on four surfaces — and because a mitigation that removes the symptom
is worth having before an argument about the cure.

## What was built, in plain language

**The demo.** A real page on the left; on the right, the record of everything
that has happened to it. Not "an AI changed a page" — everyone shows that and on
its own it is unremarkable. What is on screen beside the page is:

- the **proposal**, with the rationale in the interpreter's own words, who
  authored it (`model` or `runtime`), the interpreter's name, its confidence,
  and the delta operation by operation;
- **what the Gate weighed**, on the two axes it keeps separate — the stakes level
  with every factor it cited, and reversibility with the inverse delta spelled
  out and the count of nodes undo would have to carry;
- **the verdict** — the decision, the rule code that fired, a sentence saying
  what that rule is *for*, the runtime's own detail, and the policy that decided
  it with its fingerprint;
- **the revision** it produced and the one it replaced, with **undo as a real
  button** that proposes an inverse rather than rewinding a log.

Everything in that list already existed in the runtime. Nothing is computed for
display: the record is a pure projection of the `RuntimeEvent` stream the runtime
narrates about itself, which is what makes it impossible for the surface to show
a verdict the Gate did not reach.

**Five changes need no key at all.** Re-theme the page, swap the hero backdrop,
insert a band, remove the stats, move the quote — between them they exercise all
four delta operations, and each is a deterministic interpreter rather than a
script beside the runtime
([0057](../decisions/0057-a-preset-is-a-deterministic-interpreter.md)). Free text
goes to the model when one is configured, and the record shows which of the two
authored the proposal, because the Gate does not care.

**The page itself is a marketing page**, built from twelve of the eighteen
primitives — hero, logo cloud, feature grid, stats, quote, questions, closing
band. §4d builds the real site from these same nodes, so it had to be good enough
to stand as one.

### The thing worth clicking twice

Under the demo's policy a re-theme applies on its own and a restructure waits for
you. That is not a mock: the ceiling for `user-instruction` is `low` here rather
than the shipped `medium`, deliberately, because under the default **every**
change the demo can make would auto-apply and the hold — the most interesting
thing the runtime does — would never appear on screen. The policy is named
`demo` and its name is on every verdict (0033), so nothing about that is hidden.

The best demonstration in it is the one I did not plan: undo a change, after a
second change has touched the same node, and the Gate holds it under
`discards-later-work` with the revisions it would write over named in the
reason. 0035 working in front of a person, in three clicks.

## Where it lives, and why that is a decision

The demo is a **public route inside the portal app**
([0056](../decisions/0056-the-demo-is-public-and-shares-nothing-but-the-deployment.md)).
Three things pulled against each other:

| | |
| --- | --- |
| It has to be **seen** | One Vercel project exists and it builds `apps/portal`. A new app ships invisible until someone creates a second project by hand — and you not having been able to look at any of this is the specific problem this step exists to solve. |
| It has to be **reachable without an account** | §4d embeds it. A marketing page cannot ask a visitor to sign in to see the thing being marketed. |
| It must not **weaken the portal** | The portal is behind a session by design (0027), and the danger of an exemption is never the door — it is the next unguarded page reaching through it for a store handle. |

So: public, and sharing nothing with the portal but the deployment. Its own
registry, its own in-memory store per visitor, its own policy, no identity, no
telemetry journal. The exemption is held honest by a test that reads the source
of every unguarded page and fails if one imports `@/lib/store`, `@/lib/write`,
`@/lib/telemetry` or `@/lib/database` — auth excepted, because `/sign-in` exists
to use it.

**This is expected to be revisited at §4d**, and the record says so rather than
pretending otherwise. If the marketing site becomes its own app the demo moves
into it: it has no portal-specific import to unpick, which was the point of
building it this way.

## Decisions not explicitly specified, and why

- **A visitor gets their own copy.** One shared tree would be a multiplayer
  editor nobody asked for, and two visitors undoing each other is a worse first
  impression than no demo. State is a memory store keyed by an opaque cookie,
  evicted at 64 sessions, gone when the instance recycles — which reads to a
  visitor as the page having reset, and is the only failure mode a demo can
  afford.
- **Free text is bounded by a token bucket**, per session and per instance, both
  debited so minting sessions is not a way around the first. A public button on
  a paid API is a bill somebody else writes. A bucket rather than a counter
  because the behaviour wanted after a burst is recovery, not a deploy.
- **The chips hide themselves when they have nothing to do.** "Remove the stats"
  disappears once the stats are gone. A button whose only outcome is "nothing
  changed" is a demo of the runtime failing to do anything.
- **Answering a hold updates the card it belongs to** rather than adding a
  second one. `confirmHeld` narrates a fresh assessment and verdict but no
  intent — there is nothing left to interpret — so the projection folds those
  events onto the record that was waiting. Without that, the rail would show one
  ask as two changes and a history that never happened.
- **The demo has its own model interpreter**, told about the starter library and
  the theme registry, rather than sharing the portal's. One interpreter would
  mean one of the two surfaces describing a registry it does not use. No repairer
  is wired: a refusal here is the Gate saying no in front of a visitor, which is
  the demo working, and a quieter second attempt would be the runtime arguing
  with its own verdict on stage.
- **The record is the event stream, not the telemetry journal.** Read back
  within the request that produced it. That is what lets the demo write nothing
  to a database and still show everything.
- **Nothing was added to `src/`.** The demo is a host, and it needed no new
  runtime capability to build — which is the strongest evidence so far that the
  §4 SDK boundary is drawn in the right place.

## What was completed

A tree now renders. `src/render/` is §3: the per-request resolver, the projection
into React, and the editable decorator.

**The projection** (`src/render/render.ts`). `renderLoomTree(tree, options)`
walks the AST and returns React elements. Each node kind maps to exactly one
thing:

| node       | becomes                                            |
| ---------- | -------------------------------------------------- |
| `element`  | the registered primitive, keyed by the node's id    |
| `text`     | the string itself — no element is invented for it   |
| `slot`     | the host's projected content, or the node's own children as fallback, inside a fragment |

It is a pure function: no hooks, no state, no IO, no module-level cache, no
clock. That is what lets it run per request on an edge runtime or inside a Server
Component without the library being the thing that decides where it runs.

**Node ids are the React keys.** This is §1's stable-id scheme paying off: an id
is minted at insert and never changes on move or configure, so React reconciles a
moved subtree as a move rather than as a delete plus an insert. Component state
inside a section survives an accepted delta that relocated it.

**Rendering is total.** It always returns an element. A tree naming a primitive
this deployment does not have — because AI proposed it, or because a rollback
moved the code but not the tree — omits that node and its subtree, records one
`RenderDiagnostic`, and renders the rest of the page. In a framework where a
person writes the JSX, an unknown component is a build error and never ships;
here the tree is data that changes without a deploy, so this is a normal
condition rather than a crash. The diagnostic is a value returned beside the
element, so a host that wants strictness inspects it and picks its own status
code.

**Per-request resolution** (`src/render/request.ts`). `renderRequest` loads,
validates, and renders. `TreeSource.load` returns `unknown` on purpose: storage
is a boundary like any other, so `parseTree` runs here rather than being
something every host remembers to do. It also refuses a document whose `treeId`
is not the one the request asked for — cheap to check, and serving one tenant's
page under another's request is the failure it prevents. The rendered result
carries the parsed tree back, because the caller needs `revision` to set a cache
validator.

**The primitive contract** (`src/render/primitive.ts`). A primitive receives
three props — `loom` (node id, type, edit-mode decoration), `props` (the node's
props, unspread), and `children` — and the renderer's whole dependency on a
registry is one lookup, `resolve(type) => LoomPrimitive | undefined`. §4 owns
registration; whatever it grows into has to satisfy no more than this to be
renderable.

The unspread part is the security-relevant decision and is argued in 0009. Props
in a Loom tree are AI-authored and arrive from storage. Spreading them into a
component's props means a proposal can name `dangerouslySetInnerHTML`, `key`, or
`ref` — and the Gate cannot catch that, because at Gate time the props are a
legal `JsonObject` and the damage depends entirely on what the component does
with them. A bag needs no blocklist.

**The editable decorator** (`src/render/editable.ts`). In edit mode the render
context carries `data-loom-*` attributes the primitive spreads onto its own root
element. Every element gets `data-loom-node` and `data-loom-type`; the root
additionally gets `data-loom-tree` and `data-loom-revision`, which is exactly the
base an `EditIntent` needs — so a portal can author one from the DOM alone, and
an intent authored against a stale render names the stale revision instead of
silently claiming the current one.

The renderer never wraps anything. Zero cost when edit mode is off is literal:
`editable` is absent rather than empty, nothing is allocated, and the markup is
tag-for-tag identical (there is a test that counts). Argued in 0010, including
what it costs — text nodes are not individually addressable, and the portal will
have to address them through their nearest element ancestor.

## A bug the tests found

Writing "resolves undefined for a type nobody registered" turned up a real one.
`staticPrimitiveResolver` looked the type up with a plain index, and a primitive
type is a lowercase identifier — so `constructor`, `toString`, and `valueOf` are
all *valid* primitive types, and a tree naming one would resolve to a function
off `Object.prototype`. An AI-authored `"constructor"` rendering as a native
function is not a lookup miss anyone would debug quickly.

Both lookups keyed by a name from the tree are now own-property only: the
resolver, and slot projection (a slot named `constructor` had the same hole).
Tested in both places.

## Decisions I made that weren't specified

1. **The renderer is a separate entry point, `@loom/runtime/react`, with `react`
   as an optional peer dependency.** Same shape as the Anthropic adapter in 0005.
   A host that composes and stores trees headlessly — a service applying deltas,
   a telemetry consumer — should not pull React into its import graph. It also
   leaves room for a non-React renderer without renaming anything.

2. **`lib` gained `DOM` in `tsconfig.json`.** `@types/react` needs it. The cost
   is that `document` and `window` now typecheck as globals everywhere, which
   would not catch a browser API called from server code. Nothing in `src/`
   references either, and the alternative — a second tsconfig for the render
   module — is more machinery than the risk justifies today.

3. **An unknown primitive omits its subtree rather than promoting the children.**
   A card's contents spilling into the page body looks like a layout bug and is
   harder to diagnose than a gap. Recorded in 0008's alternatives.

4. **A slot the host does not name falls back; a slot named with `null` projects
   nothing.** The distinction is "did the host mention this slot", not "is the
   value nullish", so projecting nothing deliberately is expressible.

5. **The test primitives live in `src/testing/primitives.ts`**, beside the
   existing fixtures and doubles, so renderer tests assert against real markup
   rather than a mock's call log. `src/testing/` is not exported from the package
   root, so none of it ships.

6. **No model work this session.** §3 does not call a model, so no model id
   decision was needed; `claude-opus-5` at effort `high` remains the interpreter
   default from 0005, unchanged.

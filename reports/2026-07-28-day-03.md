## What was completed

**§2 is now complete.** The model-backed `ChangeInterpreter` is built, and a
plain-English instruction now travels the whole pipeline: intent → model →
proposal → assessment → Gate → applied tree, with events emitted at every stage.
There is one caveat, at the bottom of this report: I could not run the live
smoke test, because there is no `ANTHROPIC_API_KEY` in the cloud routine's
environment.

**The network is one method** (`src/interpretation/client.ts`).
`ModelClient.complete(request) → Result<ModelCompletion, ModelClientError>` is
the entire boundary. A completion carries the reply **text** and the model that
actually served it. Returning text rather than a parsed object is the point:
parsing, validating, and deciding what a bad answer means all stay above the
seam, where they are testable with no network and no key.

**A model drafts; the runtime names** (`draft.ts`, `materialize.ts`). A model
never produces a `TreeDelta`. It produces a draft: the same four operations, but
inserted nodes carry no `id`. `materializeDelta` mints every new id through the
existing `IdFactory` seam, and supplies `deltaId`, `treeId`, and the base
revision itself. Existing nodes can only be addressed by ids copied out of the
rendered tree; an id outside the scheme is a malformed proposal, not a new node.
Id collisions from a model are now impossible by construction rather than caught
by validation.

**The reply is schema-constrained, and the schema is a projection**
(`schema.ts`). Structured output accepts a strict subset of JSON Schema: no
recursive definitions, and no open objects. Both collide with the AST — nodes
nest, and props are arbitrary JSON. So the emitted schema unrolls nesting to a
fixed depth (4, bottoming out at a text leaf) and tags prop values one variant
per JSON type, with a `{"kind":"json","json":"[1,2]"}` escape hatch for arrays
and objects. The AST itself is untouched; the bending happens in the projection.

**The tree the model reads** (`render.ts`). An indented outline rather than the
JSON document — a fraction of the tokens, and every node's id is the first thing
on its own line, which is what the model has to copy to address anything.
Deterministic: props are key-sorted, so the same tree always produces the same
prompt. Text values are JSON-escaped, so a node whose content contains a newline
cannot forge an outline row.

**Three answers, not one** (`interpreter.ts`). The reply is a discriminated
union: a change, "the tree already satisfies this", or "I did not understand".
The latter two map onto `no-change-needed` and `not-understood`; a reply that
cannot be parsed or validated is `malformed-proposal`; a model that is down or
declines is `interpreter-unavailable`. None of the four is a rejected proposal
and none is an exception. The load-bearing distinction between "I did not
understand" and "you may not do that" survives contact with a real model.

**The vendor adapter is opt-in** (`anthropic.ts`). `@anthropic-ai/sdk` is an
*optional peer dependency* and the adapter is a separate entry point
(`@loom/runtime/anthropic`) that the package root does not re-export. A host
bringing its own model never loads it. The adapter takes the SDK's `messages`
resource structurally, so production passes the real client and tests pass a
stub — which is how its mapping (refusal, token ceiling, transport failure) is
covered offline.

## The model, and why

**`claude-opus-5`, at effort `high`**, both configurable per interpreter. I
checked the current API documentation via the `claude-api` skill rather than
recalling an id: `claude-opus-5` is current, is in the installed SDK's model
union, and supports the structured-output shape used here
(`output_config.format` with a `json_schema`). Interpretation is the one step
where being wrong is expensive — a plausible-but-wrong delta passes through a
Gate that trusts the confidence the proposer reported — and it happens per
intent, not per render, so it is not on a hot path. The model that actually
served each request is recorded in provenance rather than assumed, so a
server-side fallback would show up in the audit trail rather than hiding in it.

`ANTHROPIC_API_KEY` is read from `process.env` by the SDK. It is not committed,
not written into any file in the repo, not logged, and not recorded in
provenance — provenance carries a SHA-256 **hash** of the prompt, never the
prompt, so an audit trail can prove two proposals answered the same question
without storing what was asked.

## Decisions I made that weren't specified

1. **The delta is authored against the revision the *intent* named**, not the
   tree as it stands when the model is called. A stale intent therefore produces
   a proposal that fails to apply, reported as `not-applicable`, instead of being
   silently re-targeted at a tree the asker never saw. The cost is one wasted API
   call in that rare case; the alternative was trading a loud failure for a quiet
   wrong answer. Tested.

2. **A safety refusal maps to `interpreter-unavailable`**, with the category in
   the detail. It is the closest existing code — the interpreter could not serve
   this request — but it is not a precise fit. See open question 2.

3. **No repair loop.** A malformed reply is an error, not a retry. Day 2's open
   question 2 (should a *refused* proposal be retryable) is still yours to
   answer, and a parse-level retry is a different mechanism that would be easy to
   confuse with it. With a constrained schema, malformed replies should be rare
   enough to measure before automating around them.

4. **Duplicate prop keys are rejected**, not resolved last-wins. Two values for
   one prop is an ambiguous proposal; picking one would hide that from the Gate
   and from telemetry.

5. **The JSON Schema is hand-written, not derived from Zod.** A generated schema
   would have to be edited into the accepted subset anyway. The drift this
   invites is guarded by tests: every object asserted closed with a complete
   `required` list, an allowlist of permitted keywords (so a future edit that
   adds `minItems` or `pattern` fails locally instead of at request time), the
   unrolled depth asserted, and every fixture validated against both schemas.

6. **`parseDelta` is called on the materialized delta** even though materialize
   builds it from already-validated pieces. Its own docstring calls it "the
   boundary parse for deltas arriving from AI interpretation", so this is that
   boundary. The failure branch is unreachable by construction — like
   `requireElementRoot` in `apply.ts` — and kept for the same reason.

7. **Prompt hashing uses `crypto.subtle`**, not `node:crypto`, so the module
   stays runtime-agnostic for §3's edge resolver.

## Blocker: the live smoke test never ran

The routine's environment has **no `ANTHROPIC_API_KEY`**. I checked the process
environment and the usual credential locations; `ANTHROPIC_BASE_URL` is set (it
points at this session's own agent proxy) but no API key is exposed to the repo.

I deliberately did **not** reach for the Claude Code session's own OAuth
credential to make the test pass. It is scoped to the agent's operation rather
than to this repository, and a smoke test that only goes green inside a Claude
Code session would be worse than one that honestly skips — it would tell you the
integration works when you had no way to reproduce it.

So: everything except the live call is proven. What remains unproven is
specifically **whether the API accepts the JSON Schema I generate**. The schema
is asserted against the documented constraints (all objects closed, complete
`required`, allowlisted keywords only, no recursion), which is the strongest
guarantee available offline, but a rejection would only surface on a real
request. The moment a key is present, `pnpm test` exercises it — no code change
needed.

2. **Should `InterpretationError` gain a `refused` code?** A safety refusal
   currently maps to `interpreter-unavailable`, which is the closest fit but
   conflates "the model declined this request" with "the model is down" — a
   distinction §6 will want, since one is a content signal and the other is an
   ops signal. Nothing switches exhaustively on the union today, so adding a
   variant is additive and cheap. **Recommendation: add it**, but it changes a
   contract the pipeline and the event stream both carry, so I left it to you.

3. **Carried over, still yours: should a *rejected* proposal be retryable?**
   (Day 2, question 2.) My lean is unchanged — allow one repair attempt, record
   the original refusal in telemetry regardless, so salami-slicing is visible if
   it emerges. Not blocking §3.

4. **Confidence is still self-graded.** (Day 2, question 4.) Now that a real
   model is supplying the number, this stopped being hypothetical: Gate rules 1
   and 5 trust a value the proposer chose. Calibrating it against outcomes is a
   §6 job, but it is worth knowing that a confidently wrong model has the most
   latitude the policy allows.

5. **Where node-level provenance lives.** (Day 1, carried.) Still leaning side
   table; still not forced by anything built. Record 0003 makes it slightly more
   pressing, since the runtime now names every node and could plausibly record
   which delta did it at the same moment.

6. **Large trees will outgrow the prompt.** `renderTree` renders the whole tree
   with no truncation, deliberately — silent lossiness is worse than a big
   prompt. A tree big enough to matter will need either scope-limited rendering
   (the intent already carries `scopeNodeId`) or an outline that elides
   untouched subtrees. Not urgent; the sample tree is eight nodes.

## What was completed

**Inverse deltas** (`src/tree/inverse.ts`). Closing §1's first open question, because §2 needed
it: every operation has an exact inverse, so undo is a delta rather than a snapshot. Inversion
walks the delta forward, inverting each operation against the tree that operation actually
observed, then reverses the order. A successful inversion also proves the original delta applies,
which the pipeline reuses. The round-trip property — apply, then apply the inverse, and the tree
is byte-identical — is tested for all four operations, for multi-operation deltas, and for
deltas whose later operations depend on earlier ones.

**The intent and proposal vocabulary.** `EditIntent` is what someone wants, before interpretation:
an utterance, an origin, an optional subtree scope, and the revision it was raised against.
`ProposedChange` is what comes back: a delta, a rationale, and `Provenance` — origin, actor,
which interpreter produced it, a prompt *hash* rather than the prompt, confidence, and a
timestamp. Both are Zod-validated at the boundary.

**Change analysis** (`src/runtime/analysis.ts`). Pure facts about what a delta does, extracted
before anything judges it: how many nodes are inserted, destroyed, moved, reconfigured; which
primitive types are touched and which are destroyed; which prop keys are set or unset; and how
close to the root the shallowest touched position is. Like inversion, it walks forward so each
operation is measured against the tree it observes.

**Stakes and reversibility, assessed separately.** Stakes measure damage, via named factors that
are recorded rather than collapsed into a number — a disposition can say "removes 14 nodes and
destroys `commerce.cart`" instead of just "high". Reversibility is computed by producing the
inverse up front: a change is irreversible when undoing the tree would not undo reality (a
primitive whose effects reach a payment flow) or when the inverse would retain more content than
the runtime is willing to hold.

**The Gate** (`src/runtime/gate.ts`). A pure function from an assessment and a policy to a
disposition. No IO, no clock, no tree, no state. Six ordered rules; the first that fires wins,
and the order encodes precedence — a refusal outranks a request for confirmation, and an
irreversible change is escalated *before* the stakes ceiling gets a say, so "small but permanent"
is never quietly auto-applied.

**`GatePolicy`.** Two kinds of knob, deliberately separated. The vocabulary knobs (which
primitives and prop keys are consequential) are host-supplied and default to empty, because Loom
Core cannot know that `commerce.checkout` matters more than `layout.stack`. The structural knobs
(how big a removal is "large", how close to the root counts as restructuring) are
host-independent and ship with opinionated defaults.

**Event emission** (`src/runtime/events.ts`). Every stage emits, including the ones that fail,
because a Gate that refuses the right things is only demonstrable if refusals are recorded. §6
gets its inputs from day one even though nothing consumes them yet. Emission is fire-and-forget:
a sink that throws must not be able to fail a change the Gate already accepted.

**The pipeline** (`src/runtime/pipeline.ts`). `composeChange` sequences the stages and does
nothing else — interpretation belongs to the interpreter, judgment to the Gate, structural change
to `applyDelta`. `confirmChange` completes a held-back change, and deliberately re-assesses
against the tree as it stands *now* rather than trusting the assessment captured at proposal
time, so a confirmation cannot smuggle in a decision made about a different tree. A change the
Gate now refuses outright stays refused, even with a human saying yes.

## A design flaw this session caught and fixed

The first cut had `outOfTreeEffectTypes` feeding **both** axes: touching such a primitive raised
stakes to `critical` *and* marked the change irreversible. A test asserting "small, confident,
but irreversible → ask the user" failed, because the change was being refused outright instead.

The test was right and the design was wrong. Feeding one property into both axes double-counts
it, and it made the two axes non-orthogonal — which defeats the point of a Gate that is
"stakes- and reversibility-aware". An out-of-tree effect says nothing about how much damage the
change does; it says the damage cannot be taken back.

The fix: `outOfTreeEffectTypes` now drives reversibility only. Stakes gained a
`protected-type-removed` factor instead — destroying a protected primitive is `critical` where
merely reconfiguring one is `high`, which is a genuine damage escalation and keeps the top level
reachable. A host that wants a hard block composes the two knobs: declare the type protected and
lower `refusalFloor`.

## Decisions made that weren't explicitly specified

1. **Six ordered rules rather than a scoring function.** A score would be tunable but not
   explainable, and the Gate has to justify itself to a user, a test, and telemetry. Each rule is
   a small named pure function; precedence is the list order.

2. **Auto-apply ceilings are per origin.** `user-instruction` earns `medium`, an unrequested
   `system-signal` only `low`, `developer` `high`. Who asked is a real input to how much latitude
   a change gets, and this is the one place origin is load-bearing rather than merely recorded.

3. **Inapplicable ≠ rejected.** A proposal whose delta does not apply returns `not-applicable`,
   not `rejected`. The first is an interpreter bug; the second is a policy decision. Conflating
   them would make the telemetry useless for judging either.

4. **`confirmChange` re-assesses rather than trusting the stored assessment.** Slightly more
   work, but a confirmation arriving against a moved tree is now a `revision-mismatch` instead of
   a silently misapplied change.

5. **A `Clock` seam alongside `IdFactory`.** Events need ordering, reading a clock is a side
   effect, and every other function in the runtime is pure. Same treatment as id minting.

6. **Events carry no ids.** The sink assigns storage keys. Event identity is a §6 concern and
   inventing it now would guess at the telemetry schema.

7. **`IdFactory` grew `intentId()` and `proposalId()`.** Additive to §1's identity seam; both
   implementations updated.

## What I did not build, and why

**The model-backed interpreter.** §2 names "AI interpretation" as the first stage. What shipped is
the `ChangeInterpreter` interface plus a scripted implementation in `src/testing/`. The seam is
real and everything downstream is proven against it — but nothing in this repo yet calls a model.

That was a scope call, not an oversight. A real interpreter needs an API key, a network boundary,
a prompt-assembly strategy, and a retry/repair loop for malformed deltas; it is a substantial unit
in its own right and it needs a decision from you about credential handling in the cloud routine.
Everything in §2 that does *not* depend on it is complete. See open question 1.

## Open questions / blockers for the next session

1. **The interpreter needs a credential decision — this is the one I need from you.** To build a
   model-backed `ChangeInterpreter`, the cloud routine needs an Anthropic API key available to it.
   Options: (a) a repo/environment secret the routine reads, (b) keep the interpreter local-only
   and have the routine build everything else, (c) ship a deterministic rule-based interpreter for
   development and defer the model one until §3 is done. **Recommendation: (a)**, since without a
   real interpreter §2 cannot be demonstrated end to end, and §4's registration contract is
   supposed to be proven by real usage. Until this is answered I will continue on §3.

2. **Should a rejected proposal be retryable?** Right now a refusal is terminal for that proposal.
   A "repair loop" — feed the disposition's reasons back to the interpreter and let it propose
   something weaker — is attractive and is how the Hermes beta handled validation failures. It is
   also the obvious place for an AI to learn to launder a refusal into an acceptance by salami-
   slicing. Leaning toward: allow one repair attempt, and record the original refusal in telemetry
   regardless, so the pattern is visible if it emerges.

3. **Where node-level provenance lives** (carried over from day 1, still not forced). Telemetry
   needs to know which `DeltaId` last touched a node. Side table vs. a field on the node. Still
   leaning side table. Not yet ARCHITECTURAL, because nothing built so far depends on the answer.

4. **Confidence is interpreter-reported and therefore self-graded.** A model that is confidently
   wrong sails through rule 1 and rule 5. Calibrating it against outcome data is a §6 job, but it
   is worth naming now that the Gate currently trusts a number the proposer chose.

No ARCHITECTURAL escalation this session. The tree schema and delta model were extended
additively — `inverse.ts` is new, and nothing already built had to migrate.

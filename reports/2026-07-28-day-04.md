## What was completed

**The repair loop** (`src/runtime/pipeline.ts`, `src/runtime/interpreter.ts`).
When the Gate refuses, the refusal can be handed back for exactly one more
attempt. The shape, and why each part is the way it is:

- **`ChangeRepairer` is a separate interface**, not a method on
  `ChangeInterpreter`. A runtime handed no repairer *cannot* repair, so "this
  deployment lets AI have a second go" is a visible choice at the composition
  root rather than a property of whichever interpreter got wired in.
- **One attempt, structurally.** The repair path judges the repaired proposal and
  returns its outcome. There is no path back into itself and no counter to drift.
  A repair that is refused again is terminal.
- **Refusals only.** Not `requires-confirmation` — a person was asked, and
  answering with a smaller change nobody requested is worse than waiting. Not
  `not-applicable` — that is an interpreter bug, a different kind of repair.
- **The runtime stamps the link.** `ProposedChange.repairOf` is set by the
  pipeline from the refused proposal's id. A repairer that claims a different one
  is overruled, so a weaker second proposal cannot present itself as an unrelated
  first attempt.
- **Both dispositions are emitted**, in order: the refusal's
  `disposition-decided`, then `repair-requested`, then the repair's own
  `change-proposed` / `change-assessed` / `disposition-decided`. A repairer that
  declines emits `repair-failed` and the original refusal stands.

That last point is the one that matters for your salami-slicing concern. The loop
is **bounded, not prevented** — what makes it safe to have is that
"refused → repairOf → accepted" is a shape telemetry can find and count per
interpreter, rather than one it would have to infer. 0006 records that as an
expectation on §6.

**The Gate is untouched.** A repair is judged by the same pure function against
the same policy as the proposal it replaces. There is no second-chance policy to
keep in step with the first, and no repair knob in `GatePolicy` — the Gate judges
changes; it does not decide how many chances a proposer gets.

**The model side** (`src/interpretation/`). `modelInterpreter` now returns
`ChangeInterpreter & ChangeRepairer`; both go through one shared `propose`
function, so a repair uses the same system prompt (keeping the cacheable prefix
byte-identical), the same output schema, the same parsing, and the same rules
about what a bad answer means. New in the prompt: a paragraph stating that a
revision must be a more conservative way to satisfy the *same* request, and that
if none exists the answer is `not-understood` rather than the same change sliced
smaller. `renderDelta` shows the model the operations it proposed, so the repair
is a revision of something specific rather than a second guess at the utterance.

## Decisions I made that weren't specified

1. **A separate `ChangeRepairer` interface rather than an optional method.** An
   optional method would make the capability implicit in the object; the separate
   interface makes enabling repair something someone did on purpose. This is the
   main judgement call in the session and it is argued in 0006.

2. **`repairOf` lives on `ProposedChange`, not on `Provenance`.** It describes a
   relationship between two proposals, which is the same level as `intentId`.
   Additive and optional; nothing needed migrating.

3. **The repair prompt names the objection.** A repairer that cannot see which
   rule fired can only guess. The risk that this teaches evasion is real and is
   answered by telemetry rather than by withholding the reason — withholding it
   would produce worse repairs *and* the same evasion risk.

4. **No live repair test.** Repair shares the entire call path with
   interpretation, so a second network test would double cost and flakiness while
   proving nothing new about the transport or the schema.

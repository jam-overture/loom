## What was completed

The repository went from a bare README to a typed, tested foundation for the whole
runtime. Everything below is section 1 of the build order.

**Project scaffolding.** TypeScript in strict mode with the extra safety flags on
(`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`), Zod,
Vitest, and a `pnpm verify` script that runs typecheck and tests together. No `any`
anywhere; no lint suppressions.

**The component AST.** A discriminated union of three node kinds:

- `element` — an instance of a registered primitive, carrying JSON props and an ordered child list. The only kind that composes.
- `text` — a leaf string. Text is its own node rather than a prop so a sentence can be addressed, moved, and re-authored the same way a card can.
- `slot` — a named projection region; its children are the fallback content rendered when nothing is projected into it.

Props are restricted to a JSON value space (`src/json.ts`) so that every tree
round-trips losslessly through storage, the wire, and AI structured output.

**The NodeId scheme.** Brand-typed `NodeId`, `TreeId`, and `DeltaId`, each with a
distinct prefix so a delta id cannot be passed where a node id belongs. The
load-bearing property is stability: an id is minted once, at insert, and never
changes — not on move, not on configure. Position is a derived view; the id is the
address every downstream system (deltas, provenance, telemetry, the editable
decorator) will use. Id minting is a side effect, so it enters through an
`IdFactory` seam — production injects a random factory, tests and replay tooling
inject a deterministic sequential one.

**The tree document.** `LoomTree` is a root element plus a monotonic `revision`.
A delta names the revision it was authored against, which is how a stale AI
proposal gets rejected instead of landing on a tree that has moved on underneath
it.

**`TreeDelta` — four discrete operations.** `insert`, `remove`, `move`,
`configure`. Ordered, and applied atomically: one failing operation discards the
whole delta, so a tree is never left half-edited. Structural rules enforced at
apply time:

- inserting a subtree whose ids collide with the tree (or repeat internally) is rejected
- the root cannot be removed or moved
- a node cannot be moved into itself or into its own descendant
- indices are bounds-checked and must be integers
- `move` is a detach followed by an insert, so `index` is read against the post-detach child list

**Delta application.** `applyDelta` is pure: a tree and a delta in, a new tree or
a `TreeError` out. Nothing logs, persists, or emits — the composition runtime will
wrap this with those concerns in §2, which keeps the structural rules testable in
isolation. Structural edits preserve reference identity for subtrees off the
edited path, so the renderer will be able to skip untouched branches by reference
equality.

**Errors.** A closed `TreeError` union (12 variants) with a separate
`describeTreeError` renderer, so hosts can present or localise failures however
they like. Nothing throws across a module seam — every fallible operation returns
`Result<T, E>`.

**Zod at the boundaries.** `parseTree` and `parseDelta` take `unknown` and return
a `Result`. `parseTree` also enforces the one invariant Zod cannot express:
node ids are unique across the whole tree.

## Decisions made that weren't explicitly specified

1. **Three node kinds, not more.** No `fragment` kind — a non-visual wrapper is
   expressible as a registered `fragment` primitive, and a second way to say the
   same thing complicates every traversal. No conditional or looping nodes —
   adaptation happens by proposing a delta, not by embedding control flow the Gate
   cannot reason about.

2. **`configure` covers all three kinds via a uniform "settable surface."** Each
   node kind exposes its configuration as a JSON record: props for an element,
   `{ value }` for text, `{ name }` for a slot. This is what keeps the delta model
   at exactly four operations instead of growing one per node kind. Element props
   are an open key space (the primitive owns their meaning); text and slot each
   have one required key, so unsetting it is rejected rather than silently
   producing a malformed node.

3. **`move` semantics are detach-then-insert.** The index is interpreted against
   the child list the node has already left. Moving the first of three siblings to
   the end is index 2, not 3. Documented in the delta module and covered by a test,
   because the alternative convention is equally defensible and silent disagreement
   here would produce off-by-one bugs in the editor.

4. **The root is an element, always.** A bare text or slot root has nowhere to
   insert into, which would make the first `insert` of every tree a special case.

5. **No timestamps in the core tree.** Minting a timestamp is a side effect, and
   every function in the tree modules is pure. `revision` is the ordering
   primitive; storage and telemetry stamp their own times. (The Hermes beta library
   put `createdAt`/`updatedAt` on the Bolt document — that belongs at the storage
   layer here.)

6. **Deltas carry both `treeId` and `baseRevision`.** Applying a delta to the
   wrong tree is a distinct, named error rather than a confusing cascade of
   node-not-found failures.

7. **Ids are opaque, prefixed, lowercase-alphanumeric** rather than UUIDs. They
   are shorter in the JSON payloads AI produces and reads, and the prefix makes a
   mis-wired id obvious at a glance. Uniqueness comes from 20 base36 characters of
   entropy (~103 bits).

8. **`revision` starts at 0** and increments once per accepted delta.

## Relationship to the Hermes beta library

`hermes/lib/loom` and `hermes/docs/loom` were read as background. The concepts
carried over are the boundary discipline (a portable core with no host imports),
Zod-first schemas, brand-typed ids, and validation that distinguishes structural
from renderable validity. What deliberately did **not** carry over is the shape of
the IR: the beta models a page as a flat `warp.blocks` list of block instances,
which cannot express nesting and therefore cannot express a general adaptive UI.
This repo's AST is a real tree, and `TreeDelta` replaces re-authoring the whole
document. The two are not migration-compatible, which is expected — the beta is
prior art, not a dependency.

## Open questions / blockers for the next session

None blocking. §2 (Composition Runtime) can start immediately on top of this branch.

Questions to settle when §2 forces them, listed so they are not silently decided:

1. **Inverse deltas.** Reversibility is a Gate input, and the cheapest way to get
   real undo is for `applyDelta` to also return the inverse delta. That is
   additive (a second return field), not a schema change — but it should be
   designed alongside the Gate rather than bolted on, since "is this reversible?"
   is exactly the question the Gate asks.

2. **Where node-level provenance lives.** Telemetry (§6) needs to know which
   `DeltaId` last touched a given node. Two options: a side table keyed by
   `NodeId`, or a field on the node itself. The side table keeps the AST clean and
   avoids a schema migration; a field is cheaper to read during render. Leaning
   side table. **This one touches the tree schema if decided the other way** — I
   will flag it as ARCHITECTURAL if §6 pushes toward putting it on the node.

3. **Prop validation against a primitive's declared schema.** Right now `configure`
   accepts any JSON for element props, because the primitive registration contract
   does not exist until §4. The seam is already in place — `configureNode` is where
   a registry lookup would go. Until then, an element can hold props no primitive
   understands. Deliberate for now, tracked here so it is not forgotten.

4. **Nested slots.** Currently permitted (a slot may contain a slot). No use case
   yet; if projection semantics in §3 make it ambiguous, it becomes a validator
   rule rather than a schema change.

Nothing in this session required an ARCHITECTURAL escalation — day 1 established
the schema rather than migrating one.

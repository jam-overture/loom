## What I emphasised, and why

The syllabus line for 04 is "why position is derived and identity is minted;
what breaks without it". Three choices about how to teach that:

**The failure mode, not the mechanism.** The easy version of this lesson
explains that ids are stable and paths are not, which is true, memorable, and
teaches nothing — a reader can recite it without being able to derive it. So the
lesson is built around a single observation: *a stale id fails loudly and a
stale path resolves successfully to the wrong node.* Both schemes can be wrong;
only one is wrong out loud. Everything else in the lesson is downstream of that
sentence, including why the cheap-looking option is the expensive one.

**Deriving identity from lesson 03's ordering guarantee.** This is the
elaboration hook and the part I'd most want to survive a month. Lesson 03 taught
that operations within a delta are ordered and each sees the previous one's
effect. That property is *unwritable* under path addressing — operation 2 would
have to be authored against a tree the proposer never saw. So stable identity is
not an independent design choice that happens to sit next to ordered deltas; it
is what makes ordered deltas expressible at all. If lessons 03 and 04 read as
two unrelated facts about deltas, this lesson has failed, and the Explain-it-back
and Set E questions both target exactly that derivation.

**Who is allowed to name a node (0003).** Framed without the word "trust",
because the trust framing is the weak version. The real argument is that a
model-supplied id makes "insert a new node" and "collide with an existing one"
*byte-identical messages* — so uniqueness stops being an impossibility and
becomes a check that must run on every proposal and can only reject after the
fact. Drafts carry no `id` field, so the bad message has nowhere to live.

Deliberately left for later: the `IdFactory` as a purity seam gets one sentence
pointing at lesson 05, and provenance/telemetry get named as beneficiaries
without being explained. Both are their own lessons.

## What the exercises revealed

All six snippets were executed via `src/scratch.test.ts` and every claimed
output is a real one. Two were worth more than I expected:

**The positional-address exercise is the best thing in the lesson.** It builds
the rejected addressing scheme by hand (`at(root, [1, 0])`), resolves it before
and after an insert that has nothing to do with the target, and the address goes
from `element n_4` (the card) to `text n_1` (the word "Welcome"). Not a nearby
node — a text leaf where an element used to be, with no error, no null and no
warning. Writing the argument in prose is much less convincing than four lines
of output where the silence is the finding.

**`compareTrees` gives the "what breaks without it" empirically.** A move
reports one `changed` node with facets `["parent","position"]`. The same visual
result achieved by remove-plus-insert reports four entries — two `missing`, two
`extra` — because a destroyed subtree is reported node by node. Both trees
render identically. That contrast does more for the lesson than any assertion
about join keys, and it also explains why `move` is one of the four operations
rather than sugar over the other two.

**The `"x"` namespace finally has a reason.** Lesson 03 passed
`sequentialIdFactory("x")` without ever saying why. A fresh factory mints `n_1`,
which the fixture already used for the headline, so the insert is refused with
`duplicate-node-id`. That is now an exercise in 04 with the payoff pointing
backwards — a small piece of spacing that came free.

## Found while teaching

Nothing here was fixed in code. Items 1–3 are for the build routine; item 4 was
inside `lessons/` and is fixed in this PR.

**1. `pnpm verify` cannot pass on a fresh clone.** `verify` runs
`typecheck && build && test && portal verify`, but `typecheck` resolves
`@loom/runtime/react` and `@loom/runtime/sdk` through the package `exports` map,
which points at `dist/` — output only `build` produces. On a clean checkout
typecheck fails with four `TS2307`s in `src/cli/scaffold-fixture/`. Confirmed
pre-existing by stashing this branch and running it on clean `main`. Running
`pnpm build` once first makes `pnpm verify` exit 0 (795 + 220 tests). Cheapest
fixes are swapping the order to `build && typecheck`, or giving `tsconfig.json`
a `paths` mapping to `src/`. Worth having, since "run `pnpm verify`" is the
instruction a new contributor is given.

**2. Id uniqueness is enforced over the live tree, not over the log.**
`rejectIdCollisions` compares the incoming subtree against the ids present in
the tree *at that moment*. A delta that removes `n_4` and then inserts a node
minted as `n_4` is accepted: `n_4` is a `loom.card` at revision 0 and
`{"kind":"text","id":"n_4","value":"not the card"}` at revision 1. Executed and
confirmed. This is not reachable by accident under `randomIdFactory` — you have
to construct it, as the exercise does — but it is a few lines away under a
sequential factory, and 0028 leans on ids as the join key *across the log* for
`auditSnapshot` and `compareTrees`. So the guarantee is airtight within a
revision and rests on the minting strategy across revisions. A sentence in
`ids.ts` saying so would be enough; it may not warrant a decision record. The
lesson teaches it honestly as an open edge rather than papering over it.

**3. `compareTrees` reports a renamed slot under the `"type"` facet.**
`facetsOf` returns `["type"]` when two slot nodes' `name`s differ, but a slot has
no type — 0028's prose describes differences as being "in kind, primitive,
props, text, parent, or position". A reviewer reading an audit of a renamed slot
is told its "type" changed. Purely a naming wart, but it is in output whose
whole purpose is being readable by a person at 3am, so it is worth a `name`
facet or a rename.

**4. Two inconsistencies inside `lessons/`, fixed here.** The structure table in
`lessons/README.md` called the exercise section **Do it** while lessons 02 and
03 both title it `## Try it`; lesson 03 and the review schedule then pointed
readers back at "the 'Do it' exercises", which do not exist under that name.
Standardised on **Try it**. Separately, lesson 02's fixture diagram labelled the
body text node `"Body"` where `sampleTree` actually builds `"Body copy"` — a
reader running the exercises would have seen the mismatch. Corrected, and the
diagram's id column realigned.

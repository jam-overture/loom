# What a page assumes

A documentation page is written from somewhere. *What your app has to do* is
written from inside a request that has already happened: there is a `session`, a
`page` loaded from a store, a `db` the deployment opened. Those are the
narrator's, and a program made only of the page's own code blocks cannot see
them — which is not a fault in the page. Telling a reader to imagine a request
is how you explain a request handler.

One file per page names what its story assumes, and the generated program
imports the names the page actually uses — and only those the program does not
declare for itself. *Going to production* wires a store to `db` two sections
before it says what `db` is, which is the right order for a reader and leaves one
block reaching for something the page has not shown yet. The story lends that
block a `db`; the block that builds one keeps its own.

**The first rule that keeps this honest:** a context file may *name* what the
story assumes, and must *import* anything the runtime really provides.
`compiled.test.ts` refuses any context file that declares a name the runtime
exports, so a snippet can never be made to compile by inventing the function it
calls.

**The second rule is the one that was missing, and it is about the reader.** The
first asks whether a name is real. It never asked whether a reader could get
hold of it — so a context file could import `gatePolicySchema` from where it
really lives, the page's two blocks could call it, every check could stay green,
and anybody who copied either block got `gatePolicySchema is not defined`. The
import was in a file no reader will ever see. Eleven names on five pages were in
that state on 29 October 2026.

So: **a name the runtime provides is the reader's to import, and the page shows
the import.** A name the story lends is one the reader does not need, and it is
declared here. `db` and `session` are the narrator's; `gatePolicySchema` and
`buildElement` are the runtime's, and they are imported on the page beside the
call.

**One exception, and it is a fact rather than a sentence.** You cannot write an
`import` in the middle of an object literal, so a runtime name used *only* from
`object-body` and `function-body` fences may still be re-exported from here.
`lent.ts` checks that by reading the fences rather than taking this file's word
for it, and `lent.test.ts` fails the moment a block that could have carried the
import starts calling such a name. Three names are lent on those terms today:
`renderRequest` on *Rendering a tree*, and `createElement` with
`LoomPrimitiveProps` on *Children and slots* — none of them typed into a list
anywhere, all three derived.

A file here is hand-written. The programs in `../compiled/` are not — those are
generated by `pnpm --filter @loom/app docs:fences`.
